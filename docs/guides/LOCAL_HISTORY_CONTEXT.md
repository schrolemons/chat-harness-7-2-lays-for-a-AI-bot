# 本地历史上下文与恢复回复

只读 SnowLuma 自己的 `data/<当前配置机器人账号>/messages.db`，按允许的私聊或群聊查询；不调用 QQ API、OneBot 历史 API 或服务器漫游接口，不解密 QQ 原生数据库，不读取其他账号。

本地缓存只能提供 SnowLuma 已保存的记录。桥接掉线而 SnowLuma 仍接收并保存的消息可以回填；SnowLuma 同时停止、未收到或未保存的内容无法由本地读取补齐。读取失败使用桥接已有缓存，不回退远程拉取。

控制台 **L 层 → 生命周期组件 → 历史上下文与恢复回复**：

| 参数 | 默认 | 含义 |
| --- | --- | --- |
| 恢复后私聊最多待答消息 | 5条 | 恢复前最近的未处理私聊保留待答资格，0表示全部只作历史；新来信不占该窗口 |
| 本地历史补取上限 | 40条 | 每个会话每次启动最多从本地补取的缓存记录数，0关闭补取；不是单次模型请求的历史条数 |
| 只读本地 SnowLuma 消息缓存 | 开启 | 关闭后仍执行桥接已有消息的恢复分类，停止读取 SnowLuma 文件 |

群聊恢复前的消息全部只作历史。`replyDisposition=history` 与真实 `seenAt`、`repliedAt` 分开：取消自动待答资格不代表已读或已发送，后续真实正文阅读和发送仍按真实凭据记录。延迟补取及组件热加载不会把恢复后的新来信归为旧消息。原有任务、日程和发送凭据不因恢复分类取消。

导入不经过普通来信处理器，不触发机械补话、即时唤醒、画像提取、媒体下载或 QQ 发送。私聊待答候选仍经过本地配额检查，不为旧记录调用分类模型或自动发送拒绝话术；正常唤醒和新来信处理时允许选择回复。

实际提供给模型的内容还受 **C 层 → 上下文与记忆** 的“自动补带近期历史上限”“自动带入待处理消息上限”和“常规消息快照总上限（字符）”共同约束。后者限制一次 QQ 快照内的正文、引用、发送者、时间和收件索引，不是整个“聊天与工具历史”层或模型上下文的上限。DSH 已有会话历史继续由自身上下文和压缩规则管理。

实际装配与控制台 QQ 消息子序列按双方共用的 `dialogueSeq` 升序排列；缺少序号的旧记录保持相对位置，原始事件日志和工具调用/返回配对顺序保留。快照先为最新待处理正文分配空间，再补历史和审计信息，避免旧积压挤掉新来信正文。

`npm run test:history-context` 使用本地假数据库和隔离桥接环境；控制台测试使用本机假服务，不调用真实 QQ 或模型。核心桥接与 DSH companion 的修改需要按仓库部署约定受控加载，源码测试通过不代表现有进程已生效。

双戳与待答资格分离：窗口内明确required的消息按收件seq回应，普通消息与未压缩历史可选；历史summary不创建新任务。缺本地缓存时不回退QQ历史、漫游或消息详情API。C36记录完整pendingSeqs与观察水位；可视化按这份当时采集的资格归类，保留历史回执事实。

首条实际触发唤醒的消息固定为本次输入，不被稍后来信替换。初始回查窗口为空，后续回查包含首条中尚未回复的必答消息；普通自由消息不占窗口位置，也不挤掉已有必答。连续必答可合并，并允许绑定紧邻的后续普通补充，用一次真实发送为所答的多个seq提供回执凭据。未纳入回复的上下文不跟随盖章。自主概率增长、定时冒泡与日常自动唤醒时，历史是否回复由模型决定；私聊新消息默认必答，离线恢复旧私聊仍受privateReplyLimit限制。

限额群聊半小时批次：inputSeqs表示本次5+5可自由回应的收信，全部在唤醒前收到，不带必答义务。历史仍可从100条近期缓存读取、可自主回应，且不列入收信；本批之后的新消息留下一批。pendingSeqs继续只表示真正必答资格，不能用是否在收信窗口来推断必须回复。

当前模型历史没有的旧消息，经本地缓存读取工具补读后，在下一次请求前进入QQ对话历史投影，按原始dialogueSeq与已有QQ消息共同排序。重复读取不重复增加聊天记录；不会作为新的收信或新任务。工具调用与返回保留原配对，原始日志不删改；摘要已覆盖而当前surface无原文时允许重新回填。详情接口携带真实dialogueSeq、时间及回执资格，不能用工具调用位置冒充聊天顺序。
